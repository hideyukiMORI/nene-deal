## Round 1 — full black-box assessment (#121 / PR #122)

Booted the **real** app in a throwaway stack (`docs/security/harness/`):
PHP 8.4 + **MySQL 8.4 in strict mode = production shape** (SQLite, the dev
default, has no column-length enforcement, so the input-boundary bugs below only
reproduce on MySQL). Two tenants + admin/operator each, seeded via `phinx
migrate` + `seed.sql`, driven with `attack.sh` (38 probes / 9 categories, each
asserting PASS/EXPOSED). Modeled on nene-invoice's harness. Stack destroyed with
`down -v` after.

**Three findings — all fixed and regression-verified to EXPOSED 0:**

- **F1 (Medium)** — `POST`/`PATCH /api/v1/deals` validated type/range but not
  string length or date shape, so `account_label` > 255, `note` > 65 535, and a
  malformed `expected_close_date` reached MySQL and surfaced as an unhandled
  **500** instead of a clean 422. The sibling write endpoints
  (users/stages/settings) already validated; the Deal handlers were the outlier
  (`CreateStageHandler` even checks `mb_strlen > 64`). Fix: `DealField` gained
  `MAX_ACCOUNT_LABEL`/`MAX_NOTE` constants + strict `isValidDate()`/`isValidUlid()`,
  applied in both handlers → 422 fail-closed.
- **F2 (Low)** — `owner_user_id` was accepted unvalidated, and the `users` join
  in `PdoDealRepository` was **not** org-scoped (unlike the stage join). An org-A
  caller could set a deal's owner to an org-B user's ULID and the `GET` response
  leaked that user's email as `owner_label` (observed live: `op-b@b.test`). Low
  exploitability (needs the target's 26-char ULID, which is never exposed
  cross-tenant). Fix: org-scoped the owner **and** actor joins, plus ULID-shape
  validation on `owner_user_id` (which also closes the over-long → 500 path).
- **F3 (Low)** — `X-Powered-By: PHP/8.4.22` leaked on every response despite the
  `.htaccess` `Header always unset`, because mod_headers' unset does not catch
  PHP's `expose_php` header under mod_php. Fix: `header_remove('X-Powered-By')`
  in the front controller — authoritative and portable across Docker and HETEML.

Verified-robust (no change needed): tenant isolation (signed `org` claim is
authoritative, `X-Organization-Slug` can't override it), JWT
(`alg:none`/tamper/wrong-secret/public-dev-secret/expired all 401), RBAC
(operator 403), state transitions (won-precondition, cross-org stage rejected,
handoff idempotent), numeric strictness (float/string/negative/overflow 422,
bigint-max accepted without overflow), CSV formula neutralization + BOM, headers
+ non-reflecting CORS, RFC 9457 errors with no SQL/stack/path leak at
`APP_DEBUG=false`. Regression tests added: `CreateDealHandlerTest`,
`UpdateDealHandlerTest`, `PdoDealRepositoryTest::test_owner_label_never_leaks_a_foreign_organization_user`.
`composer check` green (261 tests); CI green; merged as PR #122. Deliverables:
`docs/security/2026-07-13-assessment.md` + `README.md` + `harness/`. Report filed
to `_work/handoff-deal-security-assessment-2026-07-13.md`.

## Round 2 — records-parity red-team (#123 / PR #124)

統合リナ followed up: nene-records' same assessment had surfaced a **Critical**
(unauthenticated read of 31 admin `GET` routes, incl. webhook signing secrets)
and a **Medium** (cross-tenant read via JWT replay on capability-unmapped
routes). Directive: prove those two classes don't exist here, first. Ported
records' `probe.sh` (self-contained boot → migrate → seed → battery → assert →
`down -v`) and added the two exhaustive matrices.

- **F-01 analog — absent.** records protected only *non-GET* methods unless a
  prefix was allow-listed, so unmapped admin GETs leaked. Deal's
  `BearerTokenMiddleware` is a **blocklist**: every method on every route is
  protected except four exact paths (`/`, `/health`, `/api/v1/auth/login`,
  `/demo/standard`). Live matrix: all 11 admin GETs (incl. the audit export —
  the most sensitive read) + mutations → **401** with no token; only `/health`
  and `/` stay open.
- **F-02 analog — absent.** records checked org only on capability-mapped
  routes. Deal binds org from the **signed JWT claim → request holder → every
  repository query's `WHERE organization_id = ?`** — universal in the data
  layer, not per-route. Live matrix: an org-B admin token replayed against
  org-A's deal / history / user / stage on 11 routes → **404** every time; list
  endpoints don't spill the other org's rows; `X-Organization-Slug` can't
  override the claim; same-org access still 200 (positive control). The user
  routes deserve a note — `UserRepository::findById` is deliberately *not*
  org-scoped (it runs on pre-auth paths), but `GetUserHandler` /
  `UpdateUserUseCase` / `DeleteUserUseCase` each re-check
  `organizationId !== $organization->id()`, so they fail closed anyway.

`probe.sh` → **PASS=34 / EXPOSED=0. No new findings** — the two classes are
avoided *by architecture* (blocklist auth + data-layer org binding), not by
luck. No source change this round; `composer check` green; CI green on PR #124.
Deliverables: `docs/security/2026-07-14-assessment-redteam.md` + README history
row + `harness/probe.sh`; `_work` report appended.
